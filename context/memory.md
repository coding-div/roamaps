## Eighteen-arrow evenly spaced port benchmark — 2026-08-20

The user requested an isolated performance and route-capacity test before any live editor change: one **normal 100×36 node** connected to eighteen different normal nodes, with seven leaves above, seven below, two left, and two right. Three deterministic cases were measured: all 18 incoming, all 18 outgoing, and a seeded mixed case with 9 incoming and 9 outgoing. Each case was run against the current central midpoint port and an experimental evenly spaced central-port model. The test is diagnostic-only and is not wired to rendering, persistence, history, or the live router.

The evenly spaced central ports use positions `i / (count + 1)` on the chosen node side. This preserves 12.5-unit spacing for seven ports on a 100-unit top/bottom side and exactly 12-unit spacing for two ports on a 36-unit left/right side. It deliberately does not attempt three left/right ports because that would be only 9 units apart, below the current 12-unit lane requirement.

All 18 connections found node-safe orthogonal routes in every case. Compared with the midpoint model, the evenly spaced experiment materially reduced post-routing parallel conflicts: all-incoming from 14 to 4, all-outgoing from 14 to 8, and mixed from 14 to 5. It did not eliminate them because lane conflicts are still a post-check in the experimental setup; the approved repair remains integrating arrow-lane legality into the 0–5 bend search.

Median full 18-route computation timings were: all-incoming 15.471 ms midpoint versus 16.312 ms evenly spaced; all-outgoing 15.086 ms versus 13.934 ms; mixed 15.941 ms versus 15.343 ms. Across the three cases the arithmetic average changed from 15.499 ms to 15.196 ms, a 1.93% reduction. This is effectively performance-neutral at this scale: evenly spaced ports improve route cleanliness substantially, not speed reliably. Do not present it as a performance optimization.

Recommended order: repair endpoint safety and integrate parallel-lane obstacles into the progressive 0–5 bend search first. Keep the evenly spaced fan-out model as a separately approved future feature; it needs a global port-assignment design because the selected connection side and the port index depend on one another.

The user then requested a direct comparison between the existing route-selection priority and a stronger port-first rule. The benchmark was refined so **shortest-path** leaves all four sides available and uses the actual staged minimum-bend then shortest-candidate router, while **port-first evenly spaced** first assigns each central connection to the side facing its leaf and a distributed port, then performs staged routing within that assigned side. Both approaches returned 18 node-safe routes in all scenarios. Port-first reduced post-check parallel conflicts from 14 to 4 in all-incoming (71.42% reduction), from 14 to 8 in all-outgoing (42.85%), and from 14 to 5 in the mixed case (64.28%).

The median timing comparison was all-incoming 22.585 ms shortest-path versus 24.972 ms port-first (+10.56%); all-outgoing 43.267 ms versus 33.079 ms (-23.54%); mixed 37.286 ms versus 21.398 ms (-42.61%). The three-scenario average changed from 34.379 ms to 26.483 ms, a 22.95% reduction. This test indicates that port-first distribution can both reduce lane conflicts and usually reduce calculation work in a dense fan-out, but it is not uniformly faster. It also deliberately changes the product’s prior priority: a distributed port can be chosen before the globally lowest-bend route. The user must explicitly decide whether this new visual-spacing priority may override minimum bend count before production implementation.

## Proposed stronger overlap solution — not yet approved

Rather than scattering separate overlap checks through Add Node, Add Joiner, and dragging, use one shared spatial rule called an interaction envelope. Each normal node gets a padded rectangular envelope based on its visible box; each joiner gets a padded circular envelope based on its visible radius. The envelope is both the invisible tablet hit area and the collision boundary, so the same rule governs placement, selection, and movement.

Placement would use a preview gate: the candidate is committed only if its envelope does not intersect another node or joiner envelope and the tap was not on an arrow’s transparent hit path. A rejected candidate is never committed, the active mode turns off, and a tablet toast explains why. There is no automatic nearest-space snap, avoiding unexpected movement away from the user’s chosen location.

Movement would use a last-valid-position clamp: the object follows the finger while its envelope is clear, then stops at the last valid position when another envelope would be crossed. This prevents accidental overlap without allowing a node or joiner to jump unpredictably. Existing routing rules remain separate: normal nodes can be routing obstacles, joiners remain non-obstacles as previously approved, and direct arrow taps in placement mode reject the placement.
